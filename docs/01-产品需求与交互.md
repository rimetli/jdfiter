# 01 产品需求与交互

> 文档基线：当前本地工程实现（Vue 3 + FastAPI + MySQL Worker）。本文区分已实现功能与后续目标，避免把规划当作现状。

## 1. 产品定位

这是一个“AI 辅助招聘筛选”系统：系统解析 PDF 简历、按岗位能力模型给出证据化评分和面试建议；最终推进、保留或拒绝必须由招聘人员决定。

当前角色只有两类：

| 角色 | 当前权限 |
|---|---|
| 管理员（ADMIN） | 初始化组织、创建普通账户、查看全部岗位、管理自己或其他用户创建的岗位 |
| 普通用户（USER） | 登录后创建并管理自己创建的岗位；前端不显示账户管理和组织切换 |

首次使用时先初始化一个组织，再创建唯一管理员。管理员在“账户管理”中创建普通用户的姓名、邮箱和密码；普通用户不能自行注册，也不需要切换组织。

## 2. 当前已实现流程

```text
登录 / 首次创建管理员
  → 创建岗位并录入 JD
  → AI 分析 JD，生成能力模型草稿
  → 人工修改每项名称、描述、分数、门槛后发布
  → 上传一个或多个 PDF 简历
  → 文本提取；扫描版 PDF 则视觉模型 OCR
  → 身份去重、写入解析任务
  → Worker 解析并生成候选人画像
  → 选择多份已解析简历，批量发起 AI 人岗分析
  → 查看评分、证据、深度/角色标签和人工结论
```

## 3. 页面说明

### 3.1 登录与账户

- `/login`：已有账户输入邮箱与密码登录。
- 尚未创建任何用户时，页面显示“创建管理员账号”。
- 管理员登录后，顶部显示“账户管理”，可创建和查看普通账户。
- 登录令牌保存在浏览器本地存储，服务端签发后有效期为 24 小时；当前前端尚未提供显式“退出登录”按钮。

### 3.2 岗位与能力模型

- 创建岗位时填写岗位名称、部门（可选）和 JD。
- “AI 分析 JD”生成能力模型草稿；草稿中的评分项、权重、门槛均可人工调整。
- 发布能力模型后岗位变为 `ACTIVE`，才能上传和评估简历。
- 岗位支持删除，不使用归档。删除时会清理该岗位的申请、任务、评估、能力模型及仅属于该岗位的简历文件；仍被其他岗位引用的候选人/文件会保留。

### 3.3 简历库与上传

- 支持单份或一次选择多份 PDF；单个文件上限 20 MB。
- 文本型 PDF 用 PyPDF 提取文字；提取文字少于 30 个字符时，使用兼容 OpenAI 接口的视觉模型进行 OCR。
- 上传阶段从 PDF 文本/OCR 结果中识别姓名和联系方式。无法识别姓名，或电话和邮箱都无法识别时，上传会被拒绝。
- 去重优先级：电话唯一；仅在没有电话时，邮箱唯一。命中后提示已存在，不重复创建候选人。数据库身份声明表的唯一约束用于避免并发上传重复。
- 简历解析完成后，可在候选人列表勾选多条记录并批量分析；已存在评估结果时需确认重评。

### 3.4 结果与人工决策

- 候选人列表显示解析/分析状态、进度、总分、等级和人工结论。
- 详情显示每个能力项的状态、分数、置信度、直接证据、证据深度和贡献角色。
- 人工结论支持 `ADVANCE`（推进）、`HOLD`（待定）、`REJECT`（拒绝），单独保存，不覆盖 AI 原始评分。

## 4. 状态模型

| 对象 | 当前状态 |
|---|---|
| 岗位 | `DRAFT`、`ACTIVE` |
| 简历解析任务 | `PENDING`、`PROCESSING`、`COMPLETED`、`FAILED` |
| 简历解析版本 | `PENDING`、`PROCESSING`、`COMPLETED`、`FAILED` |
| 人岗分析任务 | `PENDING`、`PROCESSING`、`COMPLETED`、`FAILED` |
| 能力项匹配 | `MET`、`PARTIAL`、`UNKNOWN`、`NOT_MET` |

## 5. 当前边界与待完善项

- 系统仅支持 PDF；不支持 Word、图片直接上传。
- OCR 依赖已配置且支持图片输入的模型；模型不可用或扫描件不清晰时会返回明确失败信息。
- 当前没有自动淘汰、自动发信、视频面试、向量检索或 Redis 依赖。
- 账号体系已用于登录、账户管理和岗位访问；候选人、任务、评估等全部接口的账户级数据隔离仍需继续补齐后才适合多用户生产使用。
- 不以年龄、性别、民族、婚育、健康、籍贯等非岗位能力信息作为评分依据。
