# 03 数据库设计（MySQL）

> 文档基线：`backend/app/db/models.py` 与 Alembic 迁移。数据库迁移必须以 `alembic upgrade head` 执行，不应手工改表替代迁移记录。

## 1. 通用约定

- MySQL 8、InnoDB、`utf8mb4`；主键使用自增 `BIGINT`。
- 时间由数据库写入 `DATETIME`；应用按本地时区展示。
- 状态字段使用字符串，结构化但不稳定的数据使用 JSON。
- 当前姓名、邮箱、电话字段名称保留了 `*_ciphertext`，但现有代码直接存储提取值；生产环境若处理真实个人信息，应补充应用层加密和密钥管理。
- 目前不存在全局软删除框架。岗位删除会执行关联清理；候选人和简历有 `deleted_at` 字段供后续合规删除扩展。

## 2. 核心关系

```text
organizations ─ app_users
      │             └─ job_positions ─ job_requirement_versions ─ requirement_items
      │                       └─ job_applications ─ candidate_evaluations ─ evaluation_score_details ─ evaluation_evidences
      └─ candidates ─ resume_files ─ resume_parse_versions
             └─ candidate_identity_claims
processing_tasks ── (resume_file 或 job_application)
candidate_evaluations ─ human_decisions
```

## 3. 当前表与关键字段

| 表 | 主要字段/作用 |
|---|---|
| `organizations` | `id`、`name`、`status`，当前一个系统初始化一个组织 |
| `app_users` | `organization_id`、邮箱值/哈希、`display_name`、`role`、`status`、`password_hash`；唯一约束 `(organization_id, email_hash)` |
| `job_positions` | 组织、名称、部门、JD、`status`、活动能力模型、`created_by` |
| `job_requirement_versions` | 岗位能力模型版本、摘要、评分规则版本、权重 JSON、发布状态 |
| `requirement_items` | 能力项维度、名称、描述、类型、满分、门槛、替代项、排序 |
| `candidates` | 候选人联系方式哈希和值、`owner_user_id`、来源、保留/删除信息 |
| `candidate_identity_claims` | `(organization_id, owner_user_id, identity_type, identity_hash)` 唯一；为电话或邮箱占位，阻止并发去重竞态与跨账户复用 |
| `resume_files` | 候选人、文件存储键、文件名、大小、SHA-256、预解析文本存储键、上传人 |
| `resume_parse_versions` | 解析版本、状态、解析器版本、是否 OCR、画像 JSON、错误信息 |
| `job_applications` | 岗位、候选人、简历三者的关联与阶段 |
| `processing_tasks` | MySQL 队列：类型、对象、状态、进度、锁、重试、错误和输入哈希 |
| `candidate_evaluations` | 解析版本+能力模型版本产生的总分、等级、门槛结果、模型与 Prompt 元数据 |
| `evaluation_score_details` | 能力项状态、分数、置信度、原因、`depth`、`role` 和计算快照 |
| `evaluation_evidences` | 评分直接证据的页码和原文摘录 |
| `human_decisions` | 人工 `ADVANCE/HOLD/REJECT` 结论；不覆盖 AI 结果 |

## 4. 关键约束与索引

- `app_users`：`unique(organization_id, email_hash)`。
- `job_requirement_versions`：`unique(job_id, version_no)`。
- `resume_parse_versions`：`unique(resume_file_id, version_no)`。
- `candidate_identity_claims`：`unique(organization_id, owner_user_id, identity_type, identity_hash)`，是账户内去重并发安全的关键约束。
- `processing_tasks(status, available_at, priority)`：Worker 领取可处理任务。
- `job_positions(organization_id, status, updated_at)`、`job_applications(job_id, stage, created_at)`、`candidate_evaluations(application_id, created_at)`：列表和结果查询。

## 5. 去重规则与并发处理

上传时从 PDF 解析姓名、电话、邮箱：

1. 电话存在时，只以标准化电话作为唯一身份；电话相同即视为重复。
2. 电话为空时，以邮箱作为唯一身份；邮箱相同即视为重复。
3. 姓名用于识别和展示，**不参与**当前唯一性判断。
4. 新候选人写入 `candidate_identity_claims`。若并发上传触发唯一键冲突，服务重新查询已存在声明并复用对应候选人，不产生重复候选人。

`owner_user_id` 已用于候选人和身份声明归属；简历文件记录 `uploaded_by`。普通用户的候选人、任务和评估访问会回溯校验所属岗位或上传人；管理员可查询同组织全部数据。历史数据的归属字段可能为空，普通用户不会获得这类记录的任务访问权限。

## 7. 删除行为

删除岗位时，服务会删除该岗位关联的评估、证据、人工结论、申请、任务、能力模型和评分项；只被该岗位使用的简历文件、解析版本、本地文件、候选人和身份声明也会删除。仍与其他岗位关联的数据会保留，避免误删共享候选人。
